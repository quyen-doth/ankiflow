# ADR-0004: 認証・認可を 3 層に分けて責務を分離する

| 項目 | 内容 |
| --- | --- |
| 文書ID | AF-ADR-0004 |
| 決定日 | 2026-06-30 |
| ステータス | 承認 |
| 決定者 | [hong-quyen](https://github.com/quyen-doth) |
| 関連文書 | AF-SEC-001、AF-ARC-001、AF-DB-001 |

## 1. 背景と課題

マルチユーザー化にあたり、利用者が他人のデータへ到達できないことを保証する必要が生じた。

当初の計画では、Firestore Security Rules の整備を「任意」として扱っていた。ミドルウェアと API ルートで守れば十分という判断である。

計画の見直しにおいて、この判断が**誤りであることが判明した**。

理由は次のとおりである。20 以上のクライアントファイルが Firebase Client SDK を用いて Firestore を**直接**読み書きしている。ダッシュボード、履歴、作成画面、管理画面の各コンポーネントおよびフックが該当する。この経路はミドルウェアも API ルートも通らない。

加えて、Firebase のクライアント設定は JavaScript のバンドルに含まれるため公開情報である。したがって、誰でもブラウザのコンソールから Firestore へ直接問い合わせられる。**Security Rules がなければ、他の利用者のデータが誰にでも読める。**

同時に、ADR-0003 の帰結として別の制約も存在した。Firebase Admin SDK は Edge Runtime で動作しないため、**ミドルウェアではクッキーの署名を検証できない**。存在の確認しかできない。

## 2. 決定要因

| # | 要因 | 重み |
| --- | --- | --- |
| 1 | クライアントが Firestore を直接読む経路を塞がなければならない | 必須 |
| 2 | ミドルウェアでは署名を検証できない (Edge Runtime の制約) | 制約 |
| 3 | 未認証の画面遷移は早い段階で弾きたい | 中 |
| 4 | 単一の防御が破れても被害が出ないようにしたい | 高 |

要因 1 と 2 は動かせない事実である。したがって設計はこの 2 つを起点に決まる。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | API ルートでのみ検証し、Client SDK の直接アクセスをやめる | すべての読み書きを API 経由に統一する |
| B | ミドルウェアと API ルートで守り、Security Rules は任意とする | 当初の計画 |
| C | ミドルウェア・API ルート・Security Rules の 3 層で守る | 各層に異なる責務を与える |

## 4. 決定事項

**選択肢 C を採用する。** 各層の責務を次のように分離する。

| 層 | 実装 | 責務 | 限界 |
| --- | --- | --- | --- |
| 第 1 層 | `middleware.ts` | クッキーの**存在**確認と経路の振り分け | 署名を検証しない |
| 第 2 層 | `lib/auth-guard.ts` | クッキーの**署名検証**と失効確認、UID の解決 | Admin SDK は Rules をバイパスする |
| 第 3 層 | `firestore.rules` | Client SDK からのアクセスに対する**所有者判定** | サーバーからのアクセスには効かない |

第 1 層は認証ではなく**振り分け**であると位置づける。偽造したクッキーはこの層を通過する。これは欠陥ではなく想定された挙動であり、実際の検証は第 2 層が行う。

第 1 層に責務を残した理由は要因 3 である。未ログインの利用者が画面を開いた際、API の応答を待たずにログイン画面へ誘導できる。経路によって挙動を変えており、`/api/*` には 401 の JSON を返し、画面には転送を行う。クライアントの `fetch` が HTML の転送応答を受け取ると原因の分かりにくい失敗になるためである。

第 3 層は**必須**とする。要因 1 に対する唯一の対策である。

## 5. 各選択肢の評価

### 選択肢 A — すべて API 経由に統一する

**利点。** 防御点が 1 つに集約され、理解しやすい。Security Rules を書かずに済む。監査の対象が明確になる。

**選ばなかった理由。** 既存の 20 以上のファイルを書き換える必要がある。加えて、リアルタイム購読 (`onSnapshot`) を用いている箇所が API 経由では成立しない。設定や学習言語の一覧は変更が即座に画面へ反映される必要があり、この体験を捨てることになる。

なお本案は、要因 4 の観点でも C に劣る。防御点が 1 つであるため、そこに漏れがあれば直ちに破綻する。

### 選択肢 B — Security Rules を任意とする

**利点。** 実装量が最も少ない。

**選ばなかった理由。** 要因 1 をまったく満たさない。誰でも Firestore を直接読める状態が残る。これは選択肢ではなく欠陥である。計画の見直しにおいて明確に誤りと判定した。

## 6. 影響

### 6.1 得られたもの

- クライアントからの越境アクセスがデータベース層で遮断されるようになった
- 各層の限界が明文化され、どこで何を守っているかが追跡可能になった
- 単一の層の不具合が直ちに情報漏洩につながらなくなった
- リアルタイム購読を維持したまま安全性を確保できた

### 6.2 受け入れた制約

- **Security Rules の反映が別工程になる。** アプリケーションのデプロイでは反映されない。`firebase deploy --only firestore:rules` を別途実行する必要があり、失念すると新機能がクライアントから使えない
- **規則の誤りが全利用者に影響する。** 誤った内容を反映すると、全員のクライアント側の読み書きが停止する
- **反映の順序に依存する。** 規則を伴う機能では、アプリケーションより先に規則を反映しなければならない
- **Admin SDK は Rules をバイパスする。** サーバー側ルートにおける絞り込みの漏れは、第 3 層が救ってくれない。**これが本構成における最大の弱点である**
- **層ごとに規約が増えた。** 新しいコレクションを追加する際は Rules の更新が必要であり、新しいサーバールートには `withAuth` の適用と `user_id` による絞り込みが必要である

最後から 2 番目の項目は、セキュリティ設計書 (AF-SEC-001) 第 9 章に既知の制約として記録している。

### 6.3 検証されていない範囲

Security Rules 自体の自動試験は存在しない。Firebase Emulator を要するためである。現在は分離に関する単体試験 (`verify/unit/firestore-entry-rules.test.ts` など) が規則の意図を間接的に確認しているにとどまる。

`plans/architecture/260630-firebase-auth.md` において、これは積み残しとして記録されている。
