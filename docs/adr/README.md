## 1. 本書の位置づけ

本書は、アーキテクチャ決定記録 (Architecture Decision Record、以下 ADR) の索引および記述規約である。

ADR は、AnkiFlow における重要な技術的判断を 1 件につき 1 文書として記録したものである。**何を選んだか**だけでなく、**何を検討して選ばなかったか**、および**何を代償として受け入れたか**を残すことを目的とする。

## 2. 設計書との違い

ADR と設計書は目的が異なる。混同してはならない。

| | 設計書 (AF-ARC-001 など) | ADR |
| --- | --- | --- |
| 答える問い | システムは**現在どうなっているか** | **なぜそうなったか** |
| 実装が変わったとき | 文書を**修正する** | **修正しない。** 新しい ADR を書いて旧 ADR を置き換える |
| 時制 | 現在 | 決定時点で凍結する |
| 件数 | 主題ごとに固定 | 増え続ける。削除しない |

設計書は現状に追随する生きた文書であり、ADR は決定時点の判断を保存する記録である。過去の ADR に書かれた内容が現在の実装と異なっていても、それは誤りではない。決定が後から変わった場合、旧 ADR のステータスを `置換済み` とし、新しい ADR で経緯を述べる。

## 3. 記録方針

### 3.1 記述形式

[MADR (Markdown Any Decision Records)](https://adr.github.io/madr/) に準拠する。すなわち、決定内容に加えて**検討した選択肢**と**決定要因**を明記する。

選ばなかった選択肢を残すことに意味がある。後から読む者にとって、検討済みの案を再検討する手間を省けるためである。

### 3.2 対象とする判断

すべての技術的判断を記録するわけではない。次の基準のいずれかを満たすものを対象とする。

| # | 基準 |
| --- | --- |
| 1 | 後から覆すのに大きな手戻りを伴う |
| 2 | 実装を読んだだけでは意図が読み取れず、不自然に見える |
| 3 | 明確な代替案が存在し、そちらを選ぶ余地があった |
| 4 | 利用者または運用に対して制約を課す |

ライブラリの選定や命名規則のような、容易に差し替えられる判断は対象としない。

### 3.3 文書管理情報の扱い

**ADR は他の文書と異なる簡略ヘッダーを用いる。** 通常の文書が持つ `版数` と `改訂履歴` を持たない。

理由は次のとおりである。ADR は決定時点で凍結し改訂しないため、`版数` は常に初版のままとなり、`改訂履歴` は 1 行のまま増えない。いずれも情報を持たない欄となる。加えて、ADR のステータスは文書の鮮度 (`運用中` / `改訂中`) ではなく決定の効力 (`承認` / `置換済み`) を表すため、他の文書と同じ語彙を用いることができない。

形式の統一よりも、欄が意味を持つことを優先する。この例外は文書一覧 (AF-IDX-001) 第 2.8 節にも記載する。

誤記の訂正など、決定内容に影響しない修正は本文を直接修正してよい。決定内容そのものが変わる場合は修正ではなく、新しい ADR を起こす。

### 3.4 ステータス

| ステータス | 意味 |
| --- | --- |
| 提案 | 検討中であり、まだ実装していない |
| 承認 | 決定済みであり、現在も有効である |
| 非推奨 | 有効ではあるが、新規の実装では踏襲しない |
| 置換済み | 後続の ADR によって置き換えられた。`関連文書` に後続 ADR を記載する |

### 3.5 採番と命名

- 文書ID は `AF-ADR-nnnn` (4 桁の連番)。本書自体は索引であり `AF-ADR-000` とする
- ファイル名は `nnnn-english-kebab-case.md`
- 番号は再利用しない。決定を取り消した場合もファイルを削除せず、ステータスを変更する

### 3.6 決定日

実際に判断した日を記す。文書を書いた日ではない。

過去に遡って記録した ADR については、根拠となる資料 (実装計画、コミット履歴、コード内の日付) から日付を求める。特定できない場合は月単位で記し、その旨を本文に明記する。推定した日付を確定した日付のように装ってはならない。

## 5. テンプレート

新規に ADR を追加する場合、以下を雛形として用いる。

```markdown
# ADR-nnnn: 決定の要約

| 項目 | 内容 |
| --- | --- |
| 文書ID | AF-ADR-nnnn |
| 決定日 | YYYY-MM-DD |
| ステータス | 承認 |
| 決定者 | [hong-quyen](https://github.com/quyen-doth) |
| 関連文書 | AF-ARC-001 |

## 1. 背景と課題

何が問題であったか。決定を迫られた状況を、当時の事実に基づいて記す。

## 2. 決定要因

判断の基準としたものを列挙する。優先順位がある場合はそれも示す。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | … | … |
| B | … | … |

## 4. 決定事項

どれを選んだか。そしてなぜそれが決定要因を最もよく満たすか。

## 5. 各選択肢の評価

選ばなかった案について、利点と、それでも選ばなかった理由を記す。
利点がまったくない案は、そもそも選択肢ではない。公平に書くこと。

## 6. 影響

### 6.1 得られたもの

### 6.2 受け入れた制約

代償を書かない ADR は信用できない。必ず記す。

## 7. 関連情報

実装計画、該当するコード、関連する設計書への参照。
```
