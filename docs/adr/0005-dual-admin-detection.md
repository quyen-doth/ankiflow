# ADR-0005: 管理者判定を 2 系統で維持する

| 項目 | 内容 |
| --- | --- |
| 文書ID | AF-ADR-0005 |
| 決定日 | 2026-06-30 |
| ステータス | 承認 |
| 決定者 | [hong-quyen](https://github.com/quyen-doth) |
| 関連文書 | AF-SEC-001、AF-SET-001、AF-OPS-001 |

## 1. 背景と課題

マルチユーザー化に伴い、管理者という区分が生じた。管理者はアプリケーションの所有者であり、外部 API の費用を負担する。全体設定 (機能フラグ、AI モデル) と、新規利用者向け既定データの編集を行う。

管理者であるかどうかを判定する必要が生じたが、判定が必要な場所が 2 つあり、**それぞれ参照できる情報が異なっていた**。

| 判定の場所 | 参照できるもの | 参照できないもの |
| --- | --- | --- |
| サーバーの API ルート | 環境変数、セッションクッキー | — |
| Firestore Security Rules | ID トークンの中身 | **環境変数** |

Security Rules は Firestore 上で評価されるため、アプリケーションの環境変数を読めない。これは Firebase の仕様であり、回避手段がない。

一方、ADR-0004 により Security Rules は必須の防御層である。管理者のみが編集できるデータ (`content_types`、`settings/global`、`settings/default`、`__defaults__` のテンプレート) が存在する以上、Rules 側でも管理者を判定できなければならない。

## 2. 決定要因

| # | 要因 | 重み |
| --- | --- | --- |
| 1 | Security Rules は環境変数を読めない | 制約 |
| 2 | 管理者は 1 名のみであり、増える予定がない | 高 |
| 3 | 管理者の判定を誤ると、他者の既定データを書き換えられてしまう | 高 |
| 4 | 運用の手数を増やしたくない | 中 |

要因 1 が決定的である。単一の判定方式でどちらの場所も賄うことは、原理的にできない。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | Firestore に管理者一覧のドキュメントを置き、双方がそれを参照する | 判定の根拠を 1 箇所に集約する |
| B | カスタムクレームのみを用い、サーバー側もクレームを参照する | 判定の根拠を ID トークンに一本化する |
| C | 環境変数とカスタムクレームの 2 系統を維持する | それぞれの場所で使える手段を用いる |

## 4. 決定事項

**選択肢 C を採用する。** 2 系統を並立させ、**両方の設定を必須**とする。

| 系統 | 判定方法 | 適用範囲 |
| --- | --- | --- |
| サーバー側 | セッションのメールアドレスと環境変数 `ADMIN_EMAIL` の一致 | `/api/admin/*` などの API ルート (`withAdmin`) |
| ルール側 | ID トークンのカスタムクレーム `admin:true` | Firestore Security Rules (`isAdmin()`) |

カスタムクレームは `scripts/set-admin-claim.ts` により付与する。あるいは `ADMIN_EMAIL` と一致するメールアドレスでサインアップした場合に自動付与される。

要因 1 に対する現実的な解であり、要因 2 により運用負荷が問題にならないためである。管理者が 1 名である以上、二重の設定が生じるのは 1 回きりである。

なお `NEXT_PUBLIC_ADMIN_EMAIL` という第 3 の変数も存在するが、これは**判定ではない**。管理者向け画面を表示するかどうかの制御にのみ用いる。ブラウザへ配布される値であり、セキュリティ機構ではない。この点を誤解すると重大な穴になるため、`CLAUDE.md` および AF-SEC-001 に繰り返し明記している。

## 5. 各選択肢の評価

### 選択肢 A — Firestore に管理者一覧を置く

**利点。** 判定の根拠が 1 箇所に集まる。管理者を増やす際にコードもデプロイも不要である。サーバーと Rules の双方から参照できる。

**選ばなかった理由。** Rules から他のドキュメントを参照すると、評価のたびに読み取りが発生する。費用と遅延が増えるうえ、Rules の記述が複雑になる。加えて、**その管理者一覧自体を誰が守るのか**という問題が残る。一覧を書き換えられれば管理者になれてしまうため、一覧を保護する規則が別途必要になり、循環に近い構造が生じる。

要因 2 を踏まえると、管理者が増えない前提では利点が活きない。

### 選択肢 B — カスタムクレームのみ

**利点。** 判定の根拠が ID トークン 1 つに集約される。二重の設定が不要になり、要因 4 を最もよく満たす。

**選ばなかった理由。** クレームの付与は Admin SDK による操作であり、付与を許可する条件を別途どこかに持たなければならない。結局その条件は環境変数になる。すなわち環境変数を消せるわけではない。

さらに要因 3 の観点で劣る。クレームが誤って付与された場合、サーバー側にそれを止める手段がなくなる。2 系統であれば、片方が誤っていてももう片方が防ぐ。

## 6. 影響

### 6.1 得られたもの

- Security Rules から管理者を判定できるようになり、ADR-0004 の第 3 層が管理者権限まで含めて機能するようになった
- 2 つの独立した根拠を要するため、片方の設定ミスが直ちに権限昇格につながらない
- 環境変数を変えるだけでは Firestore 上の権限が変わらない。逆も同様である

### 6.2 受け入れた制約

- **2 箇所を同期させ続ける必要がある。** 一方だけを変更すると中途半端な状態になる

| 状態 | 結果 |
| --- | --- |
| `ADMIN_EMAIL` のみ設定 | API は通るが、クライアントからの既定データ編集が Rules で拒否される |
| クレームのみ付与 | クライアントからは編集できるが、管理者用 API が 403 を返す |

- **クレームの反映に再ログインが要る。** カスタムクレームは ID トークンに埋め込まれるため、付与直後は権限が効かない。運用時にこれを知らないと不具合と誤認する
- **管理者を増やす場合に手当てが要る。** 現在の `ADMIN_EMAIL` は単一の値である。複数管理者が必要になった時点で本決定は見直しの対象となる
- **判定の根拠が 3 つの変数に分散して見える。** `ADMIN_EMAIL`、カスタムクレーム、`NEXT_PUBLIC_ADMIN_EMAIL` のうち、最後の 1 つは判定ではない。この区別を誤らないよう文書で繰り返し注意を促す必要が生じた

### 6.3 見直しの契機

要因 2 (管理者は 1 名) が崩れた時点で本決定を再検討する。複数の管理者を扱う段階では、選択肢 A の欠点であった読み取り費用よりも、環境変数の単一値という制約のほうが重くなる。
