# ADR-0002: AnkiConnect の呼び出しをクライアントサイドへ移行する

| 項目 | 内容 |
| --- | --- |
| 文書ID | AF-ADR-0002 |
| 決定日 | 2026-07-04 |
| ステータス | 承認 |
| 決定者 | [hong-quyen](https://github.com/quyen-doth) |
| 関連文書 | AF-ARC-001、AF-NFR-001、AF-SET-001 |

## 1. 背景と課題

ADR-0001 により、生成したカードは AnkiConnect を通じて Anki へ登録する構成となった。当初、この呼び出しはすべて**サーバー側**で行っていた。`lib/flashcard-service` がサーバー上から `localhost:8765` へ HTTP リクエストを送る形である。

ローカル環境ではこれで動作する。開発者の端末では、サーバーと Anki が同じ機械の上にあるためである。

Vercel へデプロイした時点でこの前提が崩れた。サーバーレス関数にとって `localhost` は関数自身であり、利用者の端末ではない。**Anki 連携の機能がすべて動作しなくなった。**

当時の回避策は、Vercel 上でカードを生成し、同期だけは自分の端末でローカルの開発サーバーを起動して実行する、というものであった。これは開発者本人にしか成立しない。マルチユーザー化を控えた時点で、他の利用者は同期を永久に実行できないことを意味する。

## 2. 決定要因

| # | 要因 | 重み |
| --- | --- | --- |
| 1 | 利用者の端末で動く Anki へ到達しなければならない | 必須 |
| 2 | マルチユーザーで成立しなければならない | 必須 |
| 3 | 利用者に追加のソフトウェア導入を強いたくない | 高 |
| 4 | 新たな運用上の構成要素を増やしたくない | 高 |
| 5 | 遅延同期 (Anki 未起動時の保存) の挙動は保ちたい | 中 |

要因 1 は物理的な制約である。サーバーから利用者端末の `localhost` へ到達する経路は、原理的に存在しない。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | サーバー側のまま維持し、利用者にローカル実行を求める | 各自が自分の端末で開発サーバーを起動して同期する |
| B | 中継サーバーまたはトンネルを設ける | 利用者端末に常駐する中継を置き、サーバーから到達可能にする |
| C | ブラウザから直接 AnkiConnect を呼び出す | サーバーはデータのみを扱い、Anki の操作はブラウザが行う |

## 4. 決定事項

**選択肢 C を採用する。**

AnkiConnect のすべての呼び出しをブラウザ側へ移す。サーバーは Firestore の読み書きに専念し、Anki の操作結果をブラウザから受け取る。処理の形は次のとおりである。

```
サーバーがデータを返す
   → ブラウザが AnkiConnect を操作する
       → ブラウザが結果をサーバーへ送り返す
           → サーバーが Firestore を更新する
```

要因 1 を満たす唯一の現実的な案であるためである。ブラウザは利用者の端末で動いているため、`localhost` が正しく Anki を指す。

技術的な裏付けとして、既存の `AnkiConnectProvider` が素の `fetch` のみを用いており、そのままブラウザで動作する見込みが立っていた。`buildNotes` と `regenerateEntryNotes` も同様であり、ロジックの書き換えを伴わずに実行場所だけを移せると判断した。

## 5. 各選択肢の評価

### 選択肢 A — サーバー側のまま維持

**利点。** 実装を変更しなくてよい。CORS の設定も不要である。開発者一人であれば、実際にこの運用で回っていた。

**選ばなかった理由。** 要因 2 を満たさない。利用者ごとにローカルの開発環境を用意させることは現実的でない。マルチユーザー化と両立しない。

### 選択肢 B — 中継またはトンネル

**利点。** サーバー側の実装を大きく変えずに要因 1 を満たせる。ブラウザの制約 (CORS、ローカルネットワークアクセス制限) を回避できる可能性がある。

**選ばなかった理由。** 要因 3 と 4 に反する。利用者は Anki と AnkiConnect に加えて中継ソフトを導入し、常駐させ、認証を設定しなければならない。導入の敷居が大きく上がる。また、中継自体が新たな障害点となり、保守の対象が増える。個人開発で担える範囲を超える。

## 6. 影響

### 6.1 得られたもの

- デプロイ環境でも Anki 連携が動作するようになった
- マルチユーザーで成立するようになった。各利用者が自分の Anki を操作する
- サーバーの責務が Firestore に限定され、構造が単純になった
- 通信がネットワークを経由しないため、登録が速い
- サーバー環境変数 `ANKI_CONNECT_URL` を廃止できた。接続先は利用者ごとに `settings/{uid}.anki_connect_url` が持つ
- 遅延同期の挙動は保たれた。実行主体がサーバーからブラウザへ移っただけである

### 6.2 受け入れた制約

いずれもブラウザの仕様に起因し、アプリケーション側で回避できない。

- **CORS の設定を利用者に求める。** AnkiConnect は既定で `http://localhost` のみを許可する。利用者はアドオンの設定で `webCorsOriginList` にアプリのオリジンを追加し、Anki を再起動しなければならない
- **失敗の原因を区別できない。** ブラウザは CORS の詳細を JavaScript へ開示しない。「Anki が起動していない」「CORS 未設定」「ローカルネットワークアクセス制限」の 3 つがいずれも `TypeError: Failed to fetch` として観測される
- **Safari を使用できない。** HTTPS のページから `localhost` への接続を許可しないためである
- **ローカルネットワークアクセス制限。** 公開オリジンから `localhost` への通信を遮断するブラウザが増えている。`webCorsOriginList` を正しく設定しても到達しない場合がある。**これは現時点で解決手段がない**

最後の項目は非機能要件書 (AF-NFR-001) 第 7 章において未解消のリスクとして記録している。

対処として、`lib/flashcard-service/client.ts` の `isLocalNetworkBlockedContext()` および `ankiConnectionErrorMessage()` が、ページのオリジンが loopback であるかによって状況を推定し、案内文を出し分けている。区別が原理的に不可能である以上、推定に基づいて複数の可能性を示す方針を採った。

### 6.3 派生した制約

- **サーバーから Anki を呼んではならない**という規約が生じた。ローカル環境では偶然動作してしまうため、規約違反が本番まで気づかれない危険がある。`CLAUDE.md` および AF-ARC-001 第 3.1 節に明記している
- 自動試験において AnkiConnect の呼び出しは代替物に置き換えている。実際の Anki における結果は担保されない (AF-TST-001 第 6 章)
