# ADR-0003: 認証に httpOnly セッションクッキーを採用する

| 項目 | 内容 |
| --- | --- |
| 文書ID | AF-ADR-0003 |
| 決定日 | 2026-06-30 |
| ステータス | 承認 |
| 決定者 | [hong-quyen](https://github.com/quyen-doth) |
| 関連文書 | AF-SEC-001、AF-ARC-001、AF-API-001 |

## 1. 背景と課題

2026 年 6 月末時点まで、AnkiFlow は単一利用者を前提としていた。利用者 ID は `LOCAL_USER_ID = 'local-user'` として 5 ファイル 9 箇所にハードコードされており、ログインの概念が存在しなかった。

マルチユーザー化にあたり、認証状態をリクエスト間でどう保持するかを決める必要が生じた。

Firebase Authentication を採用することは早期に定まっていた。争点は、Firebase が発行する ID トークンをブラウザとサーバーの間でどう受け渡すかである。

制約が 2 つあった。

1. **ブラウザが Firestore を直接読む。** 20 以上のクライアントファイルが Firebase Client SDK で Firestore を読み書きしている。したがって Client SDK 側のログイン状態も別途必要である
2. **既存の `fetch` 呼び出しが多い。** 認証情報をリクエストごとに手で付与する方式を採ると、20 箇所以上の修正が生じる

## 2. 決定要因

| # | 要因 | 重み |
| --- | --- | --- |
| 1 | 認証情報を JavaScript から読めなくしたい (XSS 対策) | 最優先 |
| 2 | CSRF に対する備えが要る | 高 |
| 3 | 既存の `fetch` 呼び出しを大量に書き換えたくない | 高 |
| 4 | Next.js のミドルウェアおよびサーバーコンポーネントから読めること | 高 |
| 5 | ログアウト後に古い資格情報を無効化できること | 中 |

要因 1 が最優先である。個人の学習記録を扱う以上、トークンの窃取は避けたい。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | ID トークンを `localStorage` に保持し、`Authorization` ヘッダーで送る | 一般的な SPA の方式 |
| B | Firebase のセッションクッキー (httpOnly) を用いる | サーバーが ID トークンをクッキーへ変換する |
| C | 自前のセッション管理をサーバー側に持つ | セッション ID を発行し、サーバー側に状態を保持する |

## 4. 決定事項

**選択肢 B を採用する。**

ログイン時、ブラウザが取得した Firebase ID トークンを `POST /api/auth/session` へ送る。サーバーは `createSessionCookie()` により有効期間 5 日のセッションクッキーを生成し、`__session` として設定する。属性は `HttpOnly; Secure; SameSite=Strict; Path=/` とする。

以降のリクエストではブラウザが自動的にクッキーを送る。ログアウトは `DELETE /api/auth/session` とし、サーバーは `revokeRefreshTokens()` を呼んだうえでクッキーを削除する。

要因 1〜5 のすべてを満たすためである。

| 要因 | どう満たすか |
| --- | --- |
| 1 | `HttpOnly` により JavaScript から読めない |
| 2 | `SameSite=Strict` により他サイトからの送信が起きない |
| 3 | ブラウザが自動送信するため、既存の `fetch` を書き換えずに済む |
| 4 | ミドルウェアおよびサーバーコンポーネントはクッキーを読める |
| 5 | `revokeRefreshTokens()` と検証時の失効確認により即座に無効化できる |

要因 3 の効果は大きかった。20 箇所以上の変更が不要になった。

## 5. 各選択肢の評価

### 選択肢 A — `localStorage` + `Authorization` ヘッダー

**利点。** SPA において最も一般的であり、資料が多い。Firebase Client SDK が持つトークンをそのまま使えるため実装が単純である。CSRF の影響を受けにくい。クロスドメインの構成に対応しやすい。

**選ばなかった理由。** 要因 1 を満たさない。`localStorage` は JavaScript から読めるため、XSS が成立した時点でトークンが窃取される。加えて要因 3 と 4 も満たさない。すべての `fetch` にヘッダーを付与する修正が必要であり、Next.js のミドルウェアは `localStorage` を読めないため経路の保護をミドルウェアで行えない。

### 選択肢 C — 自前のセッション管理

**利点。** セッションの失効を完全に制御できる。有効期間や同時ログイン数などの方針を自由に設計できる。

**選ばなかった理由。** サーバーレス環境ではセッション状態の保管先が別途必要になる。Firestore へ保存すればリクエストごとに読み取りが発生し、費用と遅延が増える。Firebase が同等の機能を提供している以上、自前で持つ理由がない。要因 5 は選択肢 B でも満たせる。

## 6. 影響

### 6.1 得られたもの

- 認証情報が JavaScript から到達不能になった
- 既存の `fetch` 呼び出しを書き換えずに済んだ
- ミドルウェアで経路を保護できるようになった (ADR-0004 の前提となる)
- ログアウトが即座に効く。失効確認を有効にしているため、古いクッキーは次のリクエストで拒否される

### 6.2 受け入れた制約

- **二重のログイン状態を保つ必要がある。** ブラウザが Client SDK で Firestore を直接読むため、Firebase Auth 側のログイン状態も並行して維持しなければならない。Security Rules は `request.auth` を参照するためである。結果として `onAuthStateChanged` による状態管理が別途必要となった
- **クライアントは認証状態の確定を待たなければならない。** `useAuth().loading === false` を確認する前に UID で問い合わせてはならない。この規約は `CLAUDE.md` に明記している
- **有効期間 5 日の固定。** 期限が切れれば再ログインが要る
- **ミドルウェアでは署名を検証できない。** Firebase Admin SDK が Edge Runtime で動作しないためである。この帰結が ADR-0004 につながる
