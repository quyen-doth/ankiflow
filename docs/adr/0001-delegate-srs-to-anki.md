## 1. 背景と課題

語彙カードを Anki で手作業により作成する場合、1 枚あたりに要する作業が多い。意味、例文、発音、品詞、レベルをそれぞれ調べ、画像と音声を用意し、出題方向の異なるカードを 1 枚ずつ作り、過去に作成済みかどうかを記憶に頼って判断する必要がある。

この負担を解消するツールを作るにあたり、対象範囲をどこまでとするかを決める必要があった。

学習ツールは大きく 2 つの領域からなる。**カードを作る**領域と、**カードを出題して復習させる**領域である。後者の中核が間隔反復 (Spaced Repetition System、以下 SRS) の出題スケジューリングである。

両方を自作すれば独立した製品になるが、開発量は数倍になる。当時は単独開発かつ個人利用が前提であった。

## 2. 決定要因

| # | 要因 | 重み |
| --- | --- | --- |
| 1 | 実際に困っているのはカード作成の手間であり、復習体験ではない | 最優先 |
| 2 | 単独開発であり、投入できる時間に限りがある | 高 |
| 3 | 学習記録は失うと取り返せない。信頼性が要る | 高 |
| 4 | 既に Anki を日常的に使っており、蓄積した学習履歴がある | 高 |
| 5 | 端末をまたいで復習したい (PC、タブレット、スマートフォン) | 中 |

要因 1 が決定的である。解こうとしている課題は「作るのが大変」であって「復習しづらい」ではない。

## 3. 検討した選択肢

| # | 選択肢 | 概要 |
| --- | --- | --- |
| A | SRS を自作し、独立した学習アプリにする | 出題、採点、スケジューリング、復習画面をすべて実装する |
| B | 出題スケジューリングを Anki に委ね、カード作成に専念する | 生成したカードを Anki へ書き出し、学習は Anki 上で行う |
| C | 既存の SRS ライブラリを組み込み、復習画面のみ自作する | スケジューリングはライブラリ、画面は自作 |

## 4. 決定事項

**選択肢 B を採用する。**

AnkiFlow の責務を「カードを作る」ことに限定し、「出題して復習させる」ことは Anki に委ねる。生成したカードは AnkiConnect を通じて利用者の Anki へ登録し、以降の学習は Anki 上で行う。端末間の同期は AnkiWeb の機構を利用する。

要因 1 に対して最も素直であり、要因 2〜5 のすべてを同時に満たす唯一の案であるためである。とりわけ要因 4 が大きい。既存の学習履歴を捨てずに済むのは B のみである。

## 5. 各選択肢の評価

### 選択肢 A — SRS を自作する

**利点。** 外部アプリへの依存がなくなる。ブラウザだけで学習が完結し、AnkiConnect の CORS 設定やアプリの起動が不要になる。カード作成から復習までの体験を一貫して設計できる。将来的に製品化する場合、この形でなければならない。

**選ばなかった理由。** 開発量が過大である。スケジューリングの実装だけでは足りず、復習画面、統計、進捗の可視化、端末間同期までを揃えて初めて Anki の代替になる。そこまで作っても、既存の学習履歴は引き継げない。要因 1 に照らせば、労力の大半が解こうとしている課題の外側に費やされる。

### 選択肢 C — ライブラリ + 自作の復習画面

**利点。** A よりは開発量が小さい。スケジューリングの品質は担保される。

**選ばなかった理由。** A の問題の大部分が残る。復習画面、統計、端末間同期は依然として自作を要し、学習履歴も引き継げない。削減できるのはアルゴリズムの実装のみであり、それは A における作業量の一部にすぎない。中途半端な位置にある。

## 6. 影響

### 6.1 得られたもの

- 開発範囲がカード作成に絞られ、AI による内容生成、音声、画像、テンプレートの設計に注力できた
- 学習の信頼性を Anki の実績に委ねられた。スケジューリングの不具合で学習記録を損なう危険がない
- 既存の学習履歴を継続して利用できる
- 端末間同期を実装せずに済んだ。AnkiWeb が担う
- カードのデータが Anki 側にも残るため、AnkiFlow が使えなくなっても学習を継続できる

### 6.2 受け入れた制約

- **Anki Desktop への依存。** 利用者は Anki を導入し、AnkiConnect アドオンを設定しなければならない。導入の敷居が上がる
- **登録時に Anki の起動が要る。** これを緩和するため、状態 `reviewed` として保存し後からまとめて同期する経路を設けた (FR-042)
- **学習状況を AnkiFlow 側から把握しにくい。** 復習の進捗は Anki が持つため、統計を出すには同期が要る
- **ブラウザ環境の制約を受ける。** AnkiConnect の呼び出しに伴う問題は ADR-0002 に詳しい
- **製品化の道が塞がる。** 他者へ提供するには Anki の導入を強いることになる

## 7. その後の経緯

本決定はその後 2 度見直され、いずれも維持された。経緯を記録する。

### 7.1 2026-06-27 — 自作 SRS への移行を検討

`plans/architecture/260627-srs-independence-roadmap.md` において、Anki への依存を解消する構想を検討した。SM-2 アルゴリズム、`/study` 画面、Firestore へのカード保存、メディア保存の 4 点を自作する内容である。

構想に留め、着手しなかった。要因 1 の判断が変わっていないためである。

### 7.2 2026-07-07 — 復習記録のログを追加

`plans/architecture/260707-srs-phase0-review-log.md` において、`review_events` コレクションを追加した。当時、`entries.review_state` に対して 2 つの経路 (LINE 経由の評価と Anki 同期) が優先順位なく書き込んでおり、一方の進捗が失われる問題があった。

この対応は本決定の変更ではない。追記のみのログを設けることで、**どちらの方向にも進めるようデータを保全する**判断であった。当該計画は「Anki-companion / standalone SRS の両方の将来に備える」と明記している。

### 7.3 2026-07-09 — FSRS の導入

`plans/architecture/260709-fsrs-integration-cron.md` において、内部の SM-2 を FSRS へ置き換えた。

これは選択肢 A への転換ではない。**内部の間隔計算は、LINE 通知で提示する語を選ぶ目的にのみ用いる** (FR-081)。学習そのものは引き続き Anki 上で行い、AnkiFlow は復習画面を持たない。

### 7.4 現在の正確な状態

誤解を避けるため、現状を明記する。

| 項目 | 担い手 |
| --- | --- |
| 出題と復習の画面 | Anki |
| 学習用のスケジューリング | Anki |
| 端末間の同期 | AnkiWeb |
| 通知で提示する語の選定 | AnkiFlow (FSRS) |
| LINE 上での評価の記録 | AnkiFlow |
| 復習記録の保全 | AnkiFlow (`review_events`、追記のみ) |

すなわち AnkiFlow は内部に間隔計算を持つが、それは通知の対象選定のための補助であり、学習の中核ではない。両者が同じ `review_state` を更新するため、新しい進捗を壊さない優先順位規則を設けている。

要件定義書 (AF-REQ-001) 第 13 章が「独自の SRS エンジン」をスコープ外としているのは、この意味においてである。
